# 指示書 WP11 — ツール説明の強化 ＋ 商品説明文を2つ目の読み取り元にできるかの実測

## 背景（オーケストレータ判断）

E2E（80件・追加60件）の FAIL の大半は「商品の種類・仕様の取り違え」で、道具は商品の意味を判定しない（SPEC §7・§8、消込表 #934 ①は回答待ち・推奨は持たせない）。その推奨の範囲として、ChatGPT への**ツール説明**を強める（WP11-1）。
また、数量の読み取りは商品名だけを使っており、WP10 の網（1/10）でも 2〜5倍の誤り（R5 の択一・約4倍の二重計上）は拾えない。楽天API は `itemCaption`（商品説明文）を返し、adapter は `Offer.caption` に取得済みだが数量判定に使っていない。**商品名と説明文で総数が食い違えば low** にする機構が効くかを、実装の前に実データで測る（WP11-2。測定だけ。実装はオーケストレータが表を見て決める）。

## WP11-1 ツール説明の強化（変更分類 B・SPEC §10 MCP を同じコミットで）

- 対象: 公開MCP・stdio MCP の `search_products`・`compare_offers` のツール説明（AI 向けの説明文）。説明文の所有箇所を grep で確認し1箇所で直す（2箇所に同じ文があれば寄せる）。
- 足す内容（文言は既存の説明の口調に合わせる。長くしすぎない）:
  1. この道具は商品の種類・仕様（本体／交換部品・付属品、純正／互換、型番・世代違い、単3／単4、炭酸／非炭酸、本体／詰め替え など）を判定しない。利用者の指定に合わない候補は、`include_terms`・`exclude_terms`（商品名で判定）や `ng_keyword` で絞ってから比べ、最終回答の前に商品名で照合すること。
  2. `confidence` が high でない候補（単価不明）と `unit_price_outlier` が true の候補は、最安・おすすめとして示さない。示す時は理由と「商品ページで確認」を添える。
  3. 送料が不明な候補を「送料込み最安」と呼ばない（既存の説明にあれば重複させない）。
- 既存の説明文の試験（文言を固定している試験）を更新。説明の長さが既存の上限・慣行を超えないか確認。

## WP11-2 商品説明文の実測（測定のみ・コード変更なし）

- 実 API で 30 検索語程度（水・お茶・トイレットペーパー・おむつ・歯磨き粉・洗剤・米・コーヒー・電池・インク・ポータブル電源・ケーブル・ナッツ・プロテイン・ティッシュ等。pages=1・30件・1秒1回）。
- 各候補で `parse_quantity(item_name)` と `parse_quantity(caption)` を取り、商品名が high の候補について次を数える:
  - (a) 説明文も high で総数が一致 (b) 説明文も high で総数が食い違う (c) 説明文が low/none。
  - (b) を題名・説明文を人が見て分類: 商品名が誤り（＝この機構で拾える本当の誤り）／説明文が誤り（＝この機構を入れると単価不明が増えるだけ）／どちらとも言えない。
  - 説明文の読み方の工夫（先頭 N 文字だけ・「内容量」「入数」「容量」の直後だけ 等）で (b) の内訳がどう変わるかも1〜2案。
- 報告: 表（件数と率）、拾える本当の誤りの実例 5件まで、増える単価不明の見込み率、推奨（入れる／入れない／条件付き）。実測データ（JSON）は公開リポジトリに入れない（scratchpad 相当の未追跡フォルダに置き、終了時に削除。オーケストレータへの報告に要約を書く）。WORKLOG に要約1行。
